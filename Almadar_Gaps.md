- **G-ORBITAL-WASM-009** [architectural] — The browser kernel's wasm linear memory only grows: one tab reaches about 540 MB after std-kflow and osama-site are opened once (114 MB on std-accounting alone) and keeps it after both close, though the guest kernels are freed (live kernels stay at 2 after the 2026-11-14 night fix). WebAssembly memory cannot shrink, so every large guest raises the tab's floor for its life. Measured again 2026-11-15 moving orb-medar-home ↔ osama-site four times in one tab: wasm 147 → 370 (first osama-site) → 498 MB (second) and flat after, while the JS heap returns to about 100 MB, the GPU process to about 180 MB and live kernels stay at 2: the owner's "about 400 MB" on the orb site is this high-water. What in osama-site peaks at about 350 MB of linear memory is not attributed yet: the wasm build installs `CountingAlloc::thread_only`, which keeps no live or peak bytes. Re-measured 2026-11-15 after the lazy-page fix: orb-medar-home ↔ osama-site in one tab now holds 121 → 143 MB (fresh page per behavior: 128 / 92 MB), so that sequence is mostly fixed; std-kflow still lifts the tab to 403 MB and keeps it on std-accounting and osama-site (osama-site fresh: 99 MB), so the remaining high-water is about 300 MB after one large guest. A fresh page per step (scratchpad `probe/fresh-vs-tab.mjs`) is the ceiling of what a per-guest instance can win. Chrome does return a dropped WebAssembly.Memory: a 400 MB memory took the renderer from 294 to 695 MB and back to 295 MB after the last reference was dropped and GC ran (scratchpad `probe/drop-mem.mjs`), but any surviving JS reference to its buffer pins all of it. Attributed 2026-11-15 (scratchpad `probe/grow-probe.mjs`, each wasm export wrapped): opening std-kflow grows the memory 76 → 401 MB in one `foldInOrder`, the viewer folding the LOAD_BEHAVIOR answer whose GUEST_CLIENT emit carries the 37 MB client program: the glue's string copy reserves 3× the text for non-ASCII (111 MB), then the fold. Natively (`fold_peak_of_a_captured_program`) that fold peaked at 386 MB and held 199 MB, because parsing JSON text into a kernel `Value` allocated every string and key on its own (1,031,547 strings, 19,680 distinct; 818,451 keys, 3,201 distinct). Fixed the same day (owner: keep the program in std-guest-session, trim copies): the value parse runs through the existing `intern` scope (held 199 → 14 MB); state frames name held values by reference like render values (EXEC-DIST-16 widened; fold text 74 → 4.8 MB); `DeliveryRecord::from_value` reads its fields instead of a `serde_json::Value` round trip (fold peak 201 → 23 MB natively); `foldInOrder` and the `Kernel` constructor take UTF-8 bytes, so the glue copies them at size instead of reserving 3×. In the browser: opening std-kflow 76 → 153 MB (was 401), the osama-site → std-kflow → std-accounting tab holds 154 MB (was 403), orb-medar-home ↔ osama-site 92 MB (was 143). Memory round 2 (same day): the program surface carries no guards and the debug registry reads on demand, so opening std-kflow grows wasm to 131 MB and the JS heap holds 59 MB (was 130; the verification timeline no longer keeps answers without a reader). Left: what a large guest still needs at its peak (std-kflow: the 37 MB program bytes, its guest kernel 24 MB, a contract query 16 MB) stays as the tab's floor until the tab closes. Fix direction for that (needs a design, host-neutral per the owner 2026-11-15, never a browser-only realm): a releasable instance API in orbital-wasm. Reproduce: the catalog sequence in scratchpad `mem-seq.mjs` (wasm buffer byteLength per step). Prevention rung: (3) the verifiers (the per-open memory budget); the fold's held and peak bytes are pinned natively by `dispatch_alloc_count::a_folded_program_is_held_in_less_memory_than_its_text`. Severity: low. Root cause: one-off.
